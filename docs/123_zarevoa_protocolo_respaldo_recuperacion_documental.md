123 — PROTOCOLO DE RESPALDO Y RECUPERACIÓN DOCUMENTAL

1. Objetivo

Establecer un sistema básico de respaldo y recuperación para proteger la documentación oficial de ZAREVOA frente a pérdidas accidentales, errores de edición, eliminación de archivos o problemas técnicos.

2. Principio general

La documentación constituye parte esencial del desarrollo de ZAREVOA y deberá mantenerse protegida mediante mecanismos que permitan recuperar información cuando sea necesario.

El repositorio principal no deberá considerarse el único punto de conservación del proyecto.

3. Repositorio principal

La documentación oficial se mantendrá organizada en el repositorio definido para ZAREVOA.

Este repositorio será la referencia principal para consultar los documentos vigentes durante las etapas de planificación y desarrollo.

4. Historial de cambios

Cuando la plataforma utilizada disponga de historial de versiones, este deberá aprovecharse para mantener trazabilidad sobre modificaciones realizadas en los archivos.

En el caso de GitHub, los cambios guardados mediante commits permiten conservar un historial que puede utilizarse para revisar o recuperar versiones anteriores.

5. Respaldo adicional

Además del repositorio principal, será recomendable mantener periódicamente una copia adicional del proyecto.

El respaldo podrá almacenarse en:

- Un dispositivo local.
- Una unidad externa.
- Un servicio confiable de almacenamiento en la nube.
- Otro sistema de respaldo definido posteriormente.

No será necesario mantener múltiples copias innecesarias, pero sí evitar depender exclusivamente de una única ubicación.

6. Frecuencia de respaldo

Durante etapas de creación intensiva de documentación se recomienda realizar respaldos con mayor frecuencia.

Como criterio general, deberá realizarse un respaldo después de:

- Incorporar una cantidad importante de documentos.
- Realizar modificaciones estructurales.
- Completar una etapa relevante del proyecto.
- Antes de efectuar cambios masivos en el repositorio.
- Antes de reorganizar o eliminar archivos.

7. Eliminación de documentos

Antes de eliminar definitivamente un documento se deberá comprobar:

1. Que realmente se encuentre duplicado, obsoleto o reemplazado.
2. Que su contenido útil esté conservado en otro documento cuando corresponda.
3. Que exista posibilidad de recuperación mediante historial o respaldo.

La eliminación deberá realizarse de manera consciente y no únicamente para ordenar visualmente el repositorio.

8. Recuperación de información

Si un archivo se elimina o modifica accidentalmente, se deberá intentar recuperar la versión correcta utilizando, según corresponda:

- Historial de GitHub.
- Versiones anteriores.
- Copias locales.
- Respaldos externos.
- Otra copia oficial disponible.

9. Verificación de respaldos

Un respaldo solo será útil si puede recuperarse correctamente.

Por ello, periódicamente deberá comprobarse que:

- Los archivos estén accesibles.
- La copia no esté incompleta.
- Los documentos principales estén incluidos.
- La estructura pueda identificarse fácilmente.

10. Seguridad

Los respaldos deberán almacenarse en ubicaciones razonablemente seguras.

Si en etapas futuras ZAREVOA incorpora información confidencial, datos comerciales sensibles o datos personales de usuarios, se deberán implementar medidas de seguridad adicionales específicas para ese tipo de información.

11. Continuidad del proyecto

El objetivo del sistema de respaldo no será únicamente proteger archivos individuales.

También deberá permitir que el desarrollo de ZAREVOA pueda continuar ante una pérdida de información, cambio de equipo, problema de cuenta o incidente tecnológico.

12. Responsabilidad documental

Antes del lanzamiento y durante las primeras etapas del proyecto, el sistema podrá mantenerse simple y práctico.

A medida que ZAREVOA crezca, el procedimiento deberá evolucionar hacia mecanismos más automatizados de respaldo, control de acceso y recuperación.

13. Principio final

Ninguna decisión importante de ZAREVOA debería depender de una única copia.

La documentación deberá mantenerse suficientemente protegida para que un error técnico o humano no implique perder el conocimiento acumulado durante el desarrollo del proyecto.
