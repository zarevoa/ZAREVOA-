132 — CRITERIOS DE ACEPTACIÓN ZAREVOA V1

1. Objetivo

Definir las condiciones mínimas que deberá cumplir ZAREVOA V1 antes de considerarse preparada para pruebas finales y posterior lanzamiento al público.

El objetivo es evitar que una funcionalidad se considere terminada únicamente porque técnicamente funciona.

2. Principio general

ZAREVOA V1 estará preparada cuando su flujo principal sea:

funcional + comprensible + estable + personalizado + realista + seguro.

La calidad de la planificación será más importante que incorporar funciones adicionales.

3. Flujo completo

Un usuario deberá poder completar sin bloqueos críticos:

Inicio → creación del viaje → Travel Profile → ZAREVOA Engine → Tu ruta recomendada → aprobación o modificación → itinerario personalizado → recomendaciones → guardado del viaje.

Si alguna etapa esencial impide completar este recorrido, V1 no deberá considerarse lista.

4. Travel Profile

Se considerará aceptado cuando:

- Las preguntas sean comprensibles.
- La información solicitada tenga utilidad real.
- El usuario pueda completar el proceso sin confusión significativa.
- Los datos obtenidos influyan efectivamente en la planificación.
- Las preferencias puedan recuperarse correctamente.

5. ZAREVOA Engine

El motor deberá demostrar que aplica las reglas propias del proyecto.

Deberá comprobarse que:

- No proponga un número excesivo de bases.
- Distribuya los días de forma razonable.
- Respete el ritmo seleccionado.
- Considere tiempos de traslado.
- Reduzca actividades en jornadas con desplazamientos importantes.
- Utilice el presupuesto como criterio adaptable.
- Priorice Must See.
- Incorpore opciones For You relevantes.
- Considere la composición del grupo sin estereotipos.
- Evite recomendaciones claramente incompatibles con el perfil.

6. Ruta recomendada

La propuesta deberá ser suficientemente clara para que el usuario comprenda:

- Dónde estará.
- En qué orden.
- Cuántos días.
- Por qué la estructura tiene sentido.

El usuario deberá poder aprobarla o modificarla antes de generar el itinerario detallado.

7. Modificación

Se considerará aceptada cuando el usuario pueda cambiar elementos relevantes sin reiniciar todo el proceso.

Los cambios deberán actualizar correctamente las partes afectadas y conservar la información que siga siendo válida.

8. Itinerario

El itinerario deberá:

- Mantener coherencia geográfica.
- Evitar horarios imposibles.
- Considerar desplazamientos.
- Adaptarse al ritmo.
- Reflejar intereses.
- Mantener un nivel razonable de actividades.
- Considerar descanso.
- Evitar saturación innecesaria.

9. Personalización perceptible

Se deberán probar perfiles diferentes utilizando destinos y duraciones similares.

Los resultados deberán mostrar diferencias razonables cuando cambien variables como:

- Ritmo.
- Presupuesto.
- Intereses.
- Must See.
- Composición del grupo.

Si todos los perfiles reciben prácticamente el mismo viaje, la personalización deberá considerarse insuficiente.

10. Datos reales

La plataforma no deberá presentar como confirmados datos variables generados únicamente por IA.

Cuando corresponda, deberán utilizarse fuentes fiables para:

- Distancias.
- Duraciones.
- Ubicaciones.
- Horarios.
- Disponibilidad.
- Precios.

Cuando un dato no pueda verificarse, deberá evitarse una falsa sensación de certeza.

11. Recomendaciones

Una recomendación deberá cumplir tres preguntas fundamentales:

1. ¿Le interesa razonablemente a este viajero?
2. ¿Existe tiempo real para realizarla?
3. ¿Tiene sentido dentro de esta ruta?

Si no cumple estas condiciones, no debería ocupar un lugar prioritario en el itinerario.

12. Monetización

Cuando existan opciones reservables o enlaces de afiliados deberá mantenerse clara la diferencia entre recomendación y monetización.

No deberá perjudicarse la calidad del viaje para favorecer una comisión.

13. Guardado y recuperación

El usuario deberá poder:

- Guardar su viaje.
- Salir.
- Regresar posteriormente.
- Recuperar la información esencial.
- Continuar trabajando sobre su planificación.

No deberá perderse el Travel Profile, la ruta o el itinerario por errores normales de navegación.

14. Experiencia móvil

Las funciones esenciales deberán probarse en diferentes tamaños de pantalla.

No deberán existir:

- Textos ilegibles.
- Botones inaccesibles.
- Elementos superpuestos.
- Desplazamientos anormales.
- Funciones disponibles únicamente en escritorio sin justificación.

15. Rendimiento

Los tiempos de espera deberán mantenerse dentro de niveles razonables.

Cuando un proceso necesite más tiempo, deberá mostrarse claramente que ZAREVOA continúa trabajando.

El usuario no deberá interpretar una espera normal como un fallo del sistema.

16. Manejo de errores

Los errores deberán:

- Mostrar mensajes comprensibles.
- Evitar pérdida innecesaria de información.
- Permitir reintentar cuando corresponda.
- Registrar información técnica suficiente para investigar el problema.

17. Seguridad básica

Antes del lanzamiento deberá comprobarse:

- Protección de cuentas.
- Gestión segura de credenciales.
- Restricción de accesos.
- Protección razonable de datos personales.
- Ausencia de claves privadas expuestas.
- Uso de conexiones seguras.

18. Privacidad y transparencia

El usuario deberá poder comprender qué información se recopila y para qué se utiliza.

Las políticas necesarias deberán estar disponibles antes de procesar datos de usuarios reales.

19. Analítica

Los eventos principales deberán registrarse correctamente para conocer:

- Dónde comienza el usuario.
- Dónde abandona.
- Si completa el Travel Profile.
- Si genera una ruta.
- Si modifica la ruta.
- Si obtiene un itinerario.
- Si guarda el viaje.
- Si interactúa con recomendaciones o productos.

20. Pruebas de escenarios

Antes del lanzamiento deberán probarse múltiples situaciones, incluyendo:

- Viaje corto.
- Viaje largo.
- Una sola base.
- Varias bases.
- Presupuesto económico.
- Presupuesto premium.
- Ritmo relajado.
- Ritmo intenso.
- Viajero individual.
- Pareja.
- Grupo.
- Familia.
- Diferentes combinaciones de intereses.

21. Errores críticos

No deberán existir errores conocidos que:

- Impidan completar el flujo.
- Eliminen viajes.
- Expongan datos.
- Generen rutas claramente imposibles.
- Bloqueen pagos, si existen.
- Presenten información potencialmente engañosa de forma sistemática.

22. Pruebas con usuarios reales

Antes de un lanzamiento amplio será recomendable realizar una etapa controlada con usuarios reales.

Sus observaciones deberán utilizarse para detectar problemas que las pruebas internas no hayan identificado.

23. Criterio de salida

ZAREVOA V1 podrá avanzar hacia lanzamiento cuando:

1. El flujo principal funcione de principio a fin.
2. La personalización sea perceptible.
3. Las rutas sean razonables.
4. Los errores críticos estén resueltos.
5. La experiencia móvil sea adecuada.
6. Los datos sensibles estén protegidos.
7. Exista capacidad para detectar y corregir problemas posteriores.

24. Principio final

La pregunta final antes de lanzar ZAREVOA V1 será:

¿Podemos entregar esta planificación a una persona real y confiar en que comprenderá el viaje, podrá utilizarlo y sentirá que fue pensado para ella?

Cuando la respuesta pueda sostenerse mediante pruebas y no solamente por expectativa, ZAREVOA V1 estará preparada para avanzar.
